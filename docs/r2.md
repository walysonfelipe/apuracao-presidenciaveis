# Publicação de resultados no Cloudflare R2

O coletor publica pelo SDK S3 no servidor, com `region: auto`, para o bucket configurado, inicialmente `eleicao`. O endereço público informado para os dados é `https://eleicoes.agendasalao.com`. A associação do domínio ao bucket, o cache e o CORS precisam ser confirmados no painel Cloudflare antes de integrar o site.

Não foram feitos uploads reais para validar essa associação. Os testes usam armazenamento substituto e credenciais fictícias. A implementação está preparada no repositório; o serviço ainda precisa ser implantado.

## Credenciais e configuração

A chave secreta compartilhada na conversa deve ser revogada e substituída. Configure a nova chave diretamente nas variáveis secretas do Railway ou em `backend/.env`, ignorado pelo Git. Não copie o segredo para documentação, frontend ou configuração de deploy versionada.

O token deve permitir operações de objeto no bucket do coletor. Credenciais S3 não devem ser confundidas com o token da API de gerenciamento da Cloudflare.

| Variável | Valor/finalidade |
| --- | --- |
| `R2_ENABLED` | `true` para habilitar; padrão `false` |
| `R2_ACCOUNT_ID` | Identificador da conta, usado para montar o endpoint S3 |
| `R2_ACCESS_KEY_ID` | ID da nova chave S3, somente no servidor |
| `R2_SECRET_ACCESS_KEY` | Segredo da nova chave S3, somente no servidor |
| `R2_BUCKET` | `eleicao` |
| `R2_PREFIX` | `resultados`; separa os arquivos desta aplicação |
| `R2_PUBLIC_BASE_URL` | `https://eleicoes.agendasalao.com` |
| `R2_PUBLISH_INTERVAL_MS` | `15000`: intervalo mínimo entre verificações para publicar |
| `R2_HEARTBEAT_INTERVAL_MS` | `60000`: intervalo entre publicações de status |
| `R2_TIMEOUT_MS` | `15000`: timeout por operação S3, incluindo tentativas do SDK |
| `R2_RETENTION_HOURS` | `48`: retenção mínima de versões antigas, com exclusão das referências atuais |

O endpoint S3 é montado como `https://<ACCOUNT_ID>.r2.cloudflarestorage.com`. Ele autentica uploads; o domínio público distribui os dados aos navegadores. Não usar o endpoint S3 como `R2_PUBLIC_BASE_URL`.

O domínio público é opcional para o upload, mas necessário para disponibilizar URLs públicas ao frontend. Sua configuração nas variáveis não cria DNS nem conecta o domínio ao bucket automaticamente.

## Executar

Após revisar [`.env.example`](../backend/.env.example), instalar as dependências e configurar os segredos:

```sh
bun run install:backend
bun run collector
```

O processo mantém coleta e publicação em tarefas independentes. Uma varredura municipal longa não precisa terminar para que resultados já recebidos sejam publicados. Falhas do R2 têm espera própria e não provocam novas consultas ao TSE.

`bun run collector:once` faz uma rodada de coleta e tenta publicar uma vez. Esse comando realiza operações reais quando `R2_ENABLED=true`; testes devem usar `bun run test:collector`.

## Arquivos e contrato público

A publicação percorre todos os contextos preparados de eleição, turno, cargo e UF. `coverage.type` é `national` para Brasil e `uf` para os documentos regionais. O catálogo anuncia os manifestos de todas as seleções já publicadas, sem sobrescrever uma UF com outra.

Exemplo para Presidente, segundo turno e SP; o código de eleição é descoberto da fonte, não fixado pelo publicador:

```text
resultados/oficial/ele2026/<eleicao>/2/1/
  brasil/<sha256>.json
  estados/sp/<sha256>.json
  status/sp.json
  manifestos/sp.json
```

O manifesto aponta para as chaves completas dos arquivos no bucket, sem URLs assinadas. O frontend deve combinar cada `key` com a base pública. Não resolver as chaves relativamente à pasta `manifestos/`.

| Arquivo | Conteúdo |
| --- | --- |
| `brasil/<hash>.json` | Identidade da eleição, abrangência e resultado nacional |
| `estados/<uf>/<hash>.json` | Resultado estadual e lista de municípios com códigos TSE/IBGE e resultados |
| `status/<uf>.json` | Heartbeat, diagnóstico da coleta, consultas/tentativas e disponibilidade por território |
| `manifestos/<uf>.json` | Schema, contexto, cobertura, revisão, publicação e referências aos arquivos |

O publicador também mantém `resultados/api/v1/config.json`, catálogo de turnos, cargos e cobertura por UF que o frontend usa para descobrir os manifestos. Ele é atualizado apenas após a publicação das referências correspondentes.

Todos usam `schemaVersion: 1`. O contexto contém `environment`, `cycle`, `election`, `round` e `office`. Os resultados reutilizam os campos do adaptador eleitoral descritos em [backend/README.md](../backend/README.md).

Um resultado ausente tem `result: null` e `availability: unavailable`. No arquivo de status, uma falha com dados anteriores tem `availability: stale`. A ausência de atualização após a parada do servidor deve ser identificada pela idade dos horários, mesmo que o último status ainda diga `available`.

Horários próprios são epoch em milissegundos UTC. A geração da fonte permanece em `result.generation` como texto recebido do TSE, com `result.idg` quando disponível. Não interpretar esse texto automaticamente como UTC nem confundir geração da fonte, consulta e publicação.

O arquivo de status é independente da revisão de votos e pode avançar enquanto o manifesto permanece igual. Sua disponibilidade e seus horários são auxiliares; não indicam uma fotografia simultânea de todas as abrangências.

## Publicação consistente e retomada

1. Capturar os resultados persistidos em um conjunto coerente para esta publicação.
2. Gerar JSONs e hashes determinísticos; horários de consulta e falhas ficam fora dos arquivos imutáveis.
3. Enviar apenas os arquivos de conteúdo ainda não registrados para esse destino.
4. Publicar o status quando necessário.
5. Atualizar o manifesto depois que os arquivos referenciados existirem.
6. Registrar o sucesso no SQLite e limpar versões antigas elegíveis.

Uma falha no upload mantém o manifesto anterior. O journal no SQLite permite retomar sem reenviar os arquivos imutáveis já confirmados. Se o banco for perdido, pode haver reenvio seguro das mesmas chaves de conteúdo.

Mudança de bucket, conta, prefixo ou contexto possui journal independente. Não editar/excluir manualmente os objetos registrados como enviados; isso invalida a premissa do journal e exige recuperação controlada.

## Retenção

A limpeza remove até 20 objetos antigos por verificação, somente entre as chaves imutáveis registradas pelo próprio publicador, depois de uma publicação consistente. Arquivos referenciados pelo manifesto atual são preservados independentemente da idade. Arquivos alheios, como imagens existentes no bucket, não são listados nem apagados.

A idade é contada desde o upload registrado, não desde quando o objeto deixou de ser referenciado. O arquivo anterior pode ser removido na próxima troca caso já tenha ultrapassado a retenção. Consumidores devem acompanhar o manifesto; URLs antigas não são um arquivo histórico permanente.

Não aplicar uma regra genérica de expiração do R2 a esse prefixo: um arquivo atual pode permanecer sem mudanças por muitos dias. A exclusão por idade, sozinha, quebraria seu manifesto. Objetos sem journal após perda do volume não são removidos automaticamente.

Uma instância coordena o país inteiro usando um único banco/journal por prefixo. A limpeza protege as referências atuais de todos os manifestos registrados, inclusive chaves reaproveitadas entre contextos. Não executar escritores independentes com volumes separados no mesmo prefixo.

## CORS e cache na Cloudflare

O exemplo [r2-cors.example.json](r2-cors.example.json) permite leitura pelas origens conhecidas do site. Ajustar `AllowedOrigins` aos endereços reais do frontend; o endereço do bucket só é uma origem se a página também for aberta nele. Para desenvolvimento local, adicionar explicitamente a origem usada, por exemplo `http://localhost:8000`.

O navegador só precisa de `GET` e `HEAD`. A escrita e a exclusão são realizadas pelo servidor, ao qual CORS não se aplica. CORS não autentica operações nem restringe quem pode acessar arquivos públicos fora de navegadores.

No domínio `eleicoes.agendasalao.com`, criar regra de cache para os JSONs sob `/resultados/`. Respeitar `Cache-Control` definido pelo coletor:

- Arquivos com hash: `public, max-age=31536000, immutable`.
- Manifestos/status: `public, max-age=0, s-maxage=5, must-revalidate`.

Não forçar o mesmo TTL longo em todos os caminhos. Configurar o cache de JSON explicitamente e verificar em uma requisição real `Content-Type`, `Cache-Control`, CORS, `ETag`, `Age` e `CF-Cache-Status`. O status do cache depende de aquecimento e localização; uma primeira resposta pode ser MISS.

## Por que não gerar URLs assinadas

URLs assinadas são úteis para transferências privadas temporárias, inclusive upload direto por um usuário. Nesta arquitetura, o coletor já possui as credenciais e envia os objetos diretamente. Os resultados são públicos e entregues por domínio com CDN, evitando assinaturas temporárias para cada visitante.

O pacote de presigner e endpoints de upload no frontend não são necessários para esse fluxo.

## Verificação e ativação

```sh
bun run test:collector
node --test test/frontend/electoral-map.mjs
```

Os testes verificam consistência do manifesto, ausência de reenvio sem mudanças, status separado, falhas, retomada, retenção, configuração, cabeçalhos, timeout e cancelamento. Nenhum desses testes envia dados ao bucket real.

Para ativar em produção: substituir a chave exposta, configurar as variáveis no Railway, confirmar domínio/CORS/cache na Cloudflare e validar uma publicação real. O frontend já descobre os manifestos pelo catálogo `resultados/api/v1/config.json`; verificar o fluxo completo de produção conforme o [contrato da API](api.md).
